== Overview

The Hybrid Automation Router (HAR) is an intelligent routing layer that
receives automation events from multiple sources (filesystem watchers,
webhooks, queues, schedules) and routes them to the best automation
target based on capabilities, tags, priorities, and configurable
strategies.

The v0.2.0 Rust workspace contains *10 crates*, including the routing
and dispatch core, the automation meta-model (`+har-meta+`), installation
domain (`+har-install+`) and shared queue ABI (`+har-abi+`). Unit and
property tests exist; the current CI baseline is not green, and end-to-end
production execution against real targets has not been validated. See
link:docs/plans/HAR-ULTRAPLAN-2026-11-23.adoc[HAR ultraplan and evidence baseline].

HAR is designed for *tight integration* with
https://github.com/hyperpolymath/rpa-elysium[RPA Elysium] while
remaining fully independent — either can be used standalone.

____
*Direction (Phase 2).* HAR is being extended into a
declarative/imperative *automation interlingua* — a tool-neutral
substrate (historically specified over A2ML, pending DEED-format
reconciliation) that lets heterogeneous automation estates
(Puppet, Salt, Terraform, Ansible) hand off and resume across each
other, with HAR as the seam. See
link:docs/decisions/0002-automation-interlingua-declarative-imperative.adoc[`+docs/decisions/0002-automation-interlingua-declarative-imperative.adoc+`].
____

Routing and dispatch *library primitives* are implemented. An optional
NATS transport publishes shared-ABI envelopes; an independent real target
consumer and its resulting effects have not been verified end-to-end.
The Idris2/Zig integration and Gleam backend remain incomplete — see
_Status_ below.

== RPA Elysium Integration

HAR and RPA Elysium are designed to share:

* *proven-fsm types* — the same state-machine vocabulary for workflow
transitions _(planned: ABI defined, not yet wired into the Rust core)_.
* *proven-queueconn* — an optional NATS publisher exists in HAR; the
RPA Elysium consumer, durable outcome semantics and integration test remain
unverified.
* *Common event schema* — Rust wire codec in `+har-abi+` and normative
Idris2 definitions in `+src/abi/+`. Historical proof claims are recorded
in `+PROOF-NEEDS.adoc+`; cross-runtime conformance is not yet demonstrated.

=== Routing demonstration (dry-run only)

[source,bash]
----
# Show which target would be chosen; this does NOT dispatch the event
har route filesystem --target rpa-elysium
----

The fully integrated HAR -> queue -> RPA Elysium execution example remains
a milestone, not a supported quick-start workflow.

== Quick Start

[source,bash]
----
# Build
cargo build --workspace

# Run tests
cargo test --workspace

# Show registered targets
har targets

# Dry-run routing only (prints decision; does not send to target)
har route filesystem

# Route with a target hint
har route web --target web-auto
----

== Routing Strategies

All seven strategies are implemented; the final target selection is
dispatched on the router’s configured strategy, and selection is
*deterministic* (it never depends on hash-map iteration order).

[width="100%",cols="32%,68%",options="header",]
|===
|Strategy |Description
|*Direct* |Target hint bypasses all rules

|*CapabilityMatch* |Match event category to target capabilities (highest
weight; ties broken by id)

|*TagMatch* |Tag-based routing rules

|*RoundRobin* |Rotate across matching targets

|*WeightedRandom* |Weight-proportional, deterministic per event (seeded
from the event id)

|*LeastLoaded* |Send to the least-busy target

|*Failover* |Highest-weight primary with an ordered fallback chain
|===

== Status

* *Phase 0 (foundation):* Repository scaffold established; green CI
baseline is blocked by current workflow failures.
* *Phase 1 (core framework):* Routing, dispatch, health and metrics
libraries exist; no production end-to-end target integration is verified.
* *Phase 2A (declarative/imperative core):* Resource graph and metadata
codec started, but complete lowering/apply/observe/lifting is pending.
* *Phase 2B (external tool federation):* Planned, not demonstrated.
* *Phase 2C (install domain):* Tier-1 hermetic simulated-executor test
landed; no arbitrary real installer capture claim.
* *Formal/FFI:* Idris2 proof history exists with conditional premises;
Ephapax is a specification, Zig FFI remains unwired. `+panels/+` and
the Gleam `+services/+` backend remain absent.
See `+PROOF-NEEDS.adoc+` for proof claims and their limits.

See link:ROADMAP.adoc[`+ROADMAP.adoc+`] for the full phased plan.
