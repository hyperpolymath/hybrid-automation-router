== Decision summary

HAR is *an implemented routing and dispatch library, an emerging automation meta-model, and a partially experimental first domain*, NOT yet an integrated production automation service. The ten-crate Rust workspace is the correct current inventory; previous seven/eight-crate summaries are stale. Phase 0 is established as repository scaffolding, but a green baseline is not established. Phase 1 has implemented routing/dispatch primitives but lacks a demonstrated ingestion-to-consumer-to-effect operational slice. Phase 2A contains graph/provenance/A2ML-codec scaffolding but not the full lowering/execution/lifting cycle. Phase 2C tier 1 has a hermetic, file-effect experiment; it does not yet capture arbitrary real installers. Phase 2B, tiers 2-5, enterprise and a deployed control plane remain later work.

The first deliverable is NOT more routing algorithms. It is a bounded, policy-checked, observable, repeatable *actual dispatch* through one real adapter to one test consumer, with operation and transport outcomes distinguished. The second is a standalone declarative graph -> plan -> apply -> observe -> lift cycle over HAR's own route domain. Do not skip those gates.

== Intension and extension

=== Intension: what HAR is for

HAR is a tool-neutral *automation coordination seam* between a desired effect and a permitted, verified realisation. Its defining properties should be:

. Accept commands/events and desired-state descriptions from heterogeneous origins.
. Represent requested effects, resources, dependencies, authority, and provenance in a stable typed model.
. Choose among eligible actions/executors subject to capabilities, cost, health, constraints and policy.
. Lower a desired state into a bounded, reviewable, deterministic, effect-aware execution plan.
. Execute or delegate to independently useful tools; report *observed outcome*, not merely transport acknowledgement.
. Preserve identity, ownership, ambiguity and loss across handoff, retries and recovery.
. Lift executed operations back toward declarative description within a declared equivalence domain, explicitly preserving non-reconstructible residue.
. Federate heterogeneous tool inventories and handoff without requiring those tools to be replaced.

The original event-router use case remains a first-class standalone product, not an expendable stepping stone. The owner-oriented broader estate vision can later connect HAR with RPA Elysium, Hypatia, Gitbot Fleet, Git Logistics, Reposystem, Pons/Panic, and capability gateways. Do not fold their responsibilities into HAR without a real integration contract.

=== Extension: what it actually covers

* Currently implemented source extension: ten Rust workspace crates (`har-abi`, `har-core`, `har-meta`, `har-install`, `har-config`, `har-dispatch`, `har-health`, `har-metrics`, `har-router`, `har-cli`).
* Current executable/verified-in-source behaviours: route selection and seven strategies, config CRUD/JSON validation, delivery adapter trait, bounded retry/circuit breaker/per-target semaphore, in-memory and JSONL dead-letter sinks, metrics snapshots, shared Rust queue envelope/receipt codec, NATS publish (optional `nats` feature), resource DAG ordering/handoff model, A2ML v0.1 graph serialization, and simulated file-install capture/uninstall/reinstall tests.
* Important limitations: CLI `route` is explicitly *dry-run* and does not dispatch. The default health probe always says healthy. The NATS live smoke test is ignored/gated and no RPA Elysium consumer effect was observed. An executor that only simulates install activity does not prove real `curl | sh` capture. There is no checked-in `har-il`, Gleam backend, PanLL HAR panel, or multi-tool adapters.
* Formal extension: `PROOF-NEEDS.adoc` records three closed Idris2 obligations and Rust property tests, but no-event-loss and no-duplicate claims rely on explicit external premises; they do NOT prove cross-process, crash-surviving, effect-level exactly-once delivery. Verify buildability and correspondence to the current Rust implementation, not proof text alone.
* Governance extension: ADR-0002 (2026-07-06) sets interlingua direction but is marked 'Proposed (owner ratification pending)'. ADR-0003 (2026-07-07) is Accepted and defines owner-directed five-tier installation order. Both currently name A2ML as carrier, while estate policy has since advanced to DEED; this requires explicit compatibility/standards adjudication, not mechanical text substitution.
* Out of active scope: speculative replacement of Puppet/Salt/Terraform/Ansible. ADR-0002 explicitly parks replacement pending sponsorship or contributors; interoperability remains active.

== Three distinct endpoints

=== U: first independently usable product

A local/controlled HAR process consumes one actual event source, authorises a requested capability, resolves one real target, transmits an envelope via an adapter, receives a consumer acknowledgement, records a correlated result, and exposes a truthful CLI status. The test includes a failing target, retry budget, dead letter, trace and replay. No privileged system mutation required. Can be used standalone without Gleam/PanLL.

=== P: production-ready product (bounded, not universal)

A defined deployment profile supporting at least one real target and one source, with authenticated admission, policy enforced on *every* route path, versioned envelopes, bounded size/queue/concurrency, explicit delivery semantics, durable operation/outcome journal, recoverable and quarantined uncertain effects, structured metrics/traces, operator runbooks, CI green, vulnerability triage, tested upgrade/rollback, and incident/reconciliation procedures. Claims are scoped per adapter and effect, not global 'exactly once'. Production is a quality gate, NOT synonymous with Phase 6 enterprise.

=== E: intended open-project end-state

A tool-neutral declarative/imperative automation interlingua with tested lowering, effect-aware lifting, semantic residuals, cross-tool resource ownership/handoff, provenance, package-install provider ladder, real adapters, federated inventory/conflict detection, and typed safety contracts. Optional downstream extensions: adaptive/cost-aware routing, estate-graph and constrained route-family optimisation, scheduler/agent federation, distributed operations and enterprise profiles. End-state does not imply replacing incumbent automation suites, requiring a single broker, or pretending irreversible effects can be undone.

* Wire: ASSESSED for Rust routing, dispatch, NATS and declared integration boundaries; external consumers not observed.

== Ultraplan: risk-ordered, resumable gates

The gates below augment, not replace, ROADMAP phases and the accepted ADR-0003 ordering. A blocked gate stops authority expansion; safe independent branches (documentation, hermetic tests) may continue. Each tranche should be a bounded, reviewable PR with evidence and rollback/forward-recovery notes.

=== G0: establish a trustworthy baseline

* Inventory workspace/features/tests/CLI and planned vs real adapters at pinned SHA; snapshot current dependency tree.
* Resolve or explicitly triage B-01..B-04; fix reusable CI workflow launch/step errors and classify all required checks.
* Refresh README, ROADMAP and TOPOLOGY with the ten-crate inventory and honest operational status. Keep historical completion percentages clearly historical.
* Record ADR-0002 ratification question and DEED/legacy-A2ML migration decision. Check both ANBFs for all six `.k9.ncl` files, record each outcome; do not claim conformance until tested.
* Acceptance: reproducible `cargo fmt --check`, `cargo clippy --workspace --all-targets`, `cargo test --workspace` and `idris2 --build har-abi.ipkg` with current pinned toolchains, or explicit fail/block reports; required CI status is explained and tracked. No new sources of truth invented.

=== G1: the first real HAR vertical slice (minimal usable)

* Add controlled event intake (manual request, local watched event, or equivalent) and an actual runtime `route -> dispatch -> adapter` operation; retain `route` as dry-run and expose an unambiguous different `dispatch` action.
* Use one selected broker/target pairing in disposable isolated test infrastructure; keep transport behind `TargetTransport`, and avoid making NATS itself part of the abstract ABI.
* Make health probe real or report `unknown` when not configured; attach stable correlation IDs and a JSON evidence receipt.
* Tests: capability denied/allowed, unavailable target, success, timeout, circuit open, dead-letter sink failure, lost ack, duplicate delivery, consumer restart.
* Acceptance: event reaches a real test consumer, evidence distinguishes transmitted/acknowledged/applied, restart behaviour is documented. Do not turn a broker ack into an effect certificate.
* Authority acceptance: a denied-capability test must also fail closed on the direct-hint and tag-rule shortcut paths, not only on normal selection (see PR #173 for the router change; G2 generalises it).

=== G2: authority, integrity and bounded failure semantics

* Apply capability verifier to every selection path (hint, tag, capability, fallback) with a common authorised-candidate set. Keep permissive verification only for explicit local demo mode.
* Define operation_id distinct from attempt_id; stable fingerprint, resource identity and owner; dedupe scope, retention and reconciliation contract.
* Introduce typed result states: rejected-before-effect, sent, broker-acknowledged, applied, effect-uncertain, recovered, recovery-conflict. Retry only when effect-safe by contract.
* Test process crash and re-delivery through a durable pilot ledger; reason about fencing, lease expiry and caller permissions; define bounded DLQ retention.
* Acceptance: failure matrix demonstrates no duplicate *business effect* for the supported idempotent fixture; ambiguous effects are quarantined rather than silently retried. The exact guarantees are bounded by fixture, platform and retention scope.

=== G3: finish Phase 2A on HAR's own routing domain

* Implement `har-il` (or a clearly named equivalent) with declarative graph, planned operations, pre/postconditions, dependency DAG, effect summaries and explicit non-invertible/residual markers.
* Lower a desired route topology into a deterministic plan, review/dry-run it, apply it to a local HAR routing configuration, observe real resulting topology, then lift an equivalent declarative description.
* Establish equivalence by resource identities and declared semantics; do NOT demand byte-identical source round-trip where lifting is lossy. Preserve unsupported annotations and an explicit loss witness/residue.
* Align Rust model with normative Idris2 spec through machine-checkable contract tests and checked ABI invariants. The proof-model-to-runtime correspondence is an explicit obligation.
* Acceptance: self-contained graph -> plan -> apply -> observe -> lift -> semantic-compare test, including precondition conflict, partial failure, unchanged resource, duplicate operation and schema version evolution. This is the 2A gate before external multi-tool claims.

=== G4: bounded recovery pilot (independent of speculative universal undo)

* Implement `docs/plans/bounded-recovery-pilot.adoc` as written: one private Unix temporary directory, regular file <=64KiB, <=128 in-session operations, cooperative single-writer fixture, resource identity/fingerprint and uncertainty states.
* First direct-executor tests, then HAR adapter tests with one attempt, then lost-ack/ambiguous-write tests at two attempts.
* No arbitrary shell commands, production paths, symlinks, hostile writers, or cross-restart guarantee at this stage. No blind Valence undo pre-check; evaluate reuse only against the contract.
* Acceptance: full interference matrix passes, conflicting modifications survive untouched, partial/unknown effects are quarantined. Production requires a further durable ledger/host isolation gate.

=== G5: Phase 2C install regularisation in owner-mandated order

* Tier 1: keep the existing `har-install` model and hermetic gate, then validate provenance/integrity/footprint on explicitly sandboxed real installers. Differentiate declared manifests, observed traces, external side effects, and files the model cannot represent. Build one declarative inventory for pinned prover/solver/language-toolchain samples.
* Tier 2: forge releases/tag-pinned sources; checksums, attestations, platform asset selection, offline/replay and rate-limit behaviour; no unpinned remote execution in tests.
* Tier 3: `.deb`/`.rpm` direct-file installs and scriptlet-effects model.
* Tier 4: define `PackageProvider` against apk/scoop/chocolatey and retrofit tiers 1-3.
* Tier 5: validate the interface against apt/dnf/Homebrew/winget, treating Guix/Nix as declarative calibration references rather than a forced tier.
* Breadth-before-depth: D1 presence/version/install/remove/upgrade/integrity/footprint across tiers first; then D2 front-end capabilities; then D3 enterprise provisioning/harnesses.
* Acceptance: same declared intent produces semantically equivalent observed state across selected providers, with explicit variance, retained provenance, no unexplained host mutation and reproducible proof-toolchain corpus. Do NOT call hermetic simulated files real host tracing.

=== G6: Phase 2B cross-tool interlingua and federation

* First establish format carrier policy: map the existing A2ML v0.1 dialect to current DEED ANBF only if the current standard can represent its semantics; define backwards-compatible read/write windows, schema version, canonicalisation (kYAML/iJSON-JCS where applicable), and cross-format golden tests.
* Import a bounded Puppet partial catalog into the common resource graph; checkpoint and transfer ownership; resume a safe slice via Salt without duplicate application.
* Add minimal Terraform (declarative) and Ansible (imperative) front-ends, use round-trip-equivalence plus explicit loss/residual checks. Never promise lossless arbitrary-language translation.
* Federate two inventories, identify ownership overlap, unknown state and stale observations; default to refusal/quarantine on conflicting authority.
* Acceptance: two independent real tools coordinate through one documented interchange contract, survive a handoff failure and explain all unresolved residues and side effects. This is the flagship interlingua claim.

=== G7: production and operational hardening

* Define deployment profile, supported platforms, resource limits, health/readiness, operator controls, telemetry and tamper-evident audit receipts. Set workload-specific latency/success/recovery SLOs only after measuring.
* Add failure drills (lost broker, credential expiry, poison message, duplicate, concurrent writer, stale graph, corrupted journal, deploy rollback) in isolated infrastructure with abort and reconciliation evidence.
* Implement minimum required source adapters, target adapters and observability feed. Keep Gleam, PanLL and external broker optional unless proven necessary for the chosen production profile.
* Acceptance: production checklist signed with applicable tests passing, zero unresolved critical security issues for the deployment, runbooks exercised, backup/restore/upgrade verified, and no unknown failure classified as successful execution.

=== G8: extended estate end-state (conditional)

* Integrate external estate decision graph as *input*, not as HAR-owned truth: inventory from Reposystem/Git Logistics, findings from Hypatia/Pons/Panic, action identities/capabilities from Gitbot Fleet and bag-of-actions.
* Permit sparse route-family enumeration, forbidden-region pruning, scored top route bundles and fallback selection only after the operational contracts are sound. Justify ranking algorithms with actual signals and evaluate deterministic reproducibility.
* Optional: adaptive scoring, PanLL/Gossamer visualisation, enterprise tenancy/SSO, proof-pipeline domain, neurophone sensor/inference sources. These are extensions, not G1/G3 blockers.
* Replacement of incumbents remains sponsor/contributor-gated, per ADR-0002; do not quietly re-scope.
